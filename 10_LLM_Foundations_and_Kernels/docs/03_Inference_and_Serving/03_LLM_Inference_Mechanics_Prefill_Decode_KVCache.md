## 2. [2026-09-08] 自回归大语言模型推理执行引擎深度拆解

### 2.1 训练与推理的根本割裂：并行 Teacher Forcing vs 串行生成死锁
初学者常有的认知误区是以为大模型的推理和训练过程差不多。在底层计算模式上，二者有着**本质的物理割裂**：

```
训练阶段 (Teacher Forcing, 彻底并行化):
输入全部已知文本: ["我", "喜欢", "深度", "学习"]
               │       │       │       │
               ▼       ▼       ▼       ▼  (一次前向传播同时并行计算出所有位置的预测)
预测下一个目标: ["喜欢", "深度", "学习", "<eos>"]
               │       │       │       │
并行比对真实标签计算交叉熵 Loss ───> 一次反向传播更新参数 (耗时: O(1) 次前向传播)

─────────────────────────────────────────────────────────────────────────────

推理阶段 (Autoregressive Loop, 严格串行依赖):
Step 1: ["我"] ───────────────────────────> 经过全网络 ──> 预测出 "喜欢"
Step 2: ["我", "喜欢"] ─────────────────────> 经过全网络 ──> 预测出 "深度"
Step 3: ["我", "喜欢", "深度"] ───────────────> 经过全网络 ──> 预测出 "学习"
Step 4: ["我", "喜欢", "深度", "学习"] ─────────> 经过全网络 ──> 预测出 "<eos>" (终止)
(耗时: 生成 N 个 Token 必须强制循环运行 N 次前向传播!)
```

- **训练时（并行）**：利用下三角**因果掩码（Causal Mask）**阻断未来视线，整个序列哪怕长达 8k，输入给 GPU 矩阵乘法一次前向传播就能算完所有 Token 的交叉熵损失。
- **推理时（串行）**：模型在生成第 $t$ 个词之前，根本不知道第 $t$ 个词是什么！后续的所有输入都依赖前面生成的输出。这种马尔可夫式的自回归链条导致生成过程**物理上无法跨步并行**，必须一轮轮循环推进。

### 2.2 推理执行的双阶段范式：Prefill (预填充) 与 Decode (逐字解码)

在大模型服务框架（如 vLLM、TensorRT-LLM、Ollama）中，一次完整的用户请求被严格划分为两个阶段：

```
                    ┌─────────────────────────┐
                    │ 用户输入 Prompt (长度 S) │
                    └────────────┬────────────┘
                                 │
                                 ▼
┌───────────────────────────────────────────────────────────────────────────┐
│ 阶段一：Prefill 阶段 (Prompt Processing / 预填充)                          │
│ • 特征：将用户输入的 S 个 Token 一次性全部送入模型                           │
│ • 作用：计算出第一个生成的词（产生首字延迟 TTFT, Time-To-First-Token）         │
│ • 附带核心任务：在各层缓存 Prompt 中所有词的 Key 和 Value 向量 (初始化 KV Cache) │
│ • 物理性质：计算密集型 (Compute-Bound)，GPU Tensor Core 核心利用率极高       │
└────────────────────────────────┬──────────────────────────────────────────┘
                                 │
                                 ▼ (生成出第 1 个新词)
┌───────────────────────────────────────────────────────────────────────────┐
│ 阶段二：Decode 阶段 (Token Generation / 逐字自回归解码)                     │
│ • 特征：进入 While 循环，每次仅向模型输入最新生成的 1 个 Token                 │
│ • 作用：结合历史 KV Cache 生成第 2、3、... 直至命中终止符 <eos>             │
│ • 性能指标：逐字延迟 (TPOT, Time-Per-Output-Token，决定“打字机”流式吐字速度)   │
│ • 物理性质：访存密集型 (Memory-Bandwidth Bound)，GPU 计算单元大量空转等待显存搬运│
└───────────────────────────────────────────────────────────────────────────┘
```

### 2.3 为什么不用每次从头算？—— KV Cache 机制与显存爆炸公式

#### 1. 朴素自回归的致命缺陷（计算浪费）
如果没有工程优化，生成第 $t$ 个词时把 $[x_1, \dots, x_{t-1}]$ 全部再次送进模型：
- 在自注意力计算中，历史词 $x_1, \dots, x_{t-1}$ 的特征向量并没有改变；
- 重新对它们做 $W_q, W_k, W_v$ 投影并算注意力，使得生成长度为 $N$ 的文本需要进行 $O(N^2)$ 的重复矩阵计算，随着对话变长，速度会急剧变慢直至瘫痪。

#### 2. KV Cache 的数学机理
因果自注意力的公式为：
$$\text{Attention}(Q, K, V) = \text{Softmax}\left(\frac{Q K^T}{\sqrt{d_k}} + M\right) V$$
- 当生成第 $t$ 个词时，我们**只需要计算当前第 $t$ 个词的 Query 向量 $q_t = x_t W_q$**。
- 这个 $q_t$ 只需要去和“历史上所有词的 Key 向量”算点积，然后对“历史上所有词的 Value 向量”做加权求和。
- 历史所有词的 Key 和 Value 向量在生成那一刻就已经确定，未来永远不会改变！
- **KV Cache 策略**：
  在 Prefill 阶段把 Prompt 对应的所有 $K$ 和 $V$ 存在显存池中；在 Decode 阶段，新词计算出自己的 $k_t, v_t$ 后追加（Append）到显存缓存池中。每一轮 Decode 只需要算**单向量与矩阵的乘法（GEMV）**，时间复杂度直接从 $O(N^2)$ 降为 $O(N)$！

#### 3. KV Cache 显存占用严密公式
设大模型参数配置如下：
- 模型层数：$n_{\text{layers}}$
- 键值注意力头数：$n_{\text{kv\_heads}}$（若为 MHA 则等于头数 $h$；若为 GQA 则远小于 $h$）
- 每个头的维度：$d_{\text{head}}$（通常为 128）
- 当前上下文序列总长度：$L$
- 批处理大小（Batch Size）：$b$
- 数据存储精度：每个参数占 $P$ 字节（FP16 / BF16 为 2 字节）

单次请求所消耗的 KV Cache 显存量为（因包含 Key 和 Value 两个矩阵，故乘 2）：
$$\text{Memory}_{\text{KV}} = 2 \times n_{\text{layers}} \times n_{\text{kv\_heads}} \times d_{\text{head}} \times L \times b \times P \text{ Bytes}$$

> [!WARNING]
> **长文本上下文下的“显存黑洞”**：
> 以 LLaMA-2 70B（MHA 结构，$n_{\text{layers}}=80, n_{\text{kv\_heads}}=64, d_{\text{head}}=128$）为例，若上下文达到 $L=8192$，单并发（$b=1$）在 FP16 下的 KV Cache 显存高达：
> $$2 \times 80 \times 64 \times 128 \times 8192 \times 1 \times 2 \text{ Bytes} \approx 21.47\text{ GB}!$$
> 仅仅存放一个用户的历史键值缓存就需要超过 20GB 显存，这就是为什么现代大模型（LLaMA-3、Mistral）必须全面改用 **分组查询注意力（GQA, Grouped-Query Attention）** 将 $n_{\text{kv\_heads}}$ 压缩 8 倍的核心原因！

### 2.4 从高维向量到人类语言：采样引擎 (Sampling Engine) 的数学流转

当最后一层 Transformer 输出当前位置的隐藏向量 $h_t \in \mathbb{R}^d$ 后，它必须经历以下数学流转才能变成人类看到的“词”：

```
隐藏状态 ht ∈ R^d
       │
       ▼ (1. LM Head 线性投影: logits = ht · W_head)
未归一化对数概率 Logits ∈ R^V (V 为词表大小, 如 128,000)
       │
       ▼ (2. Temperature 缩放: z_i = logits_i / T)
缩放后的得分 z ∈ R^V
       │
       ▼ (3. Top-K 截断: 仅保留得分最高的前 K 个候选, 其余置为 -inf)
       │
       ▼ (4. Top-P / Nucleus 截断: 按概率降序累加, 截取累积和达到 P 的最小集合, 其余置为 -inf)
       │
       ▼ (5. Softmax 归一化: P_i = exp(z_i) / Σ exp(z_j))
概率分布 P ∈ [0, 1]^V (且 Σ P_i = 1)
       │
       ▼ (6. 多项式采样 Multinomial Sampling / 贪婪选择 argmax)
选出胜出的 Token ID: 3797
       │
       ▼ (7. Detokenizer 查词表)
解码为文本: "学习"
       │
       ▼ (8. 终止判定)
检查 ID 是否等于 <|endoftext|> 或 <|im_end|>？
  ├── 是 ──> 终止推理循环
  └── 否 ──> 将 "学习" 对应的 Token ID 作为下一轮的输入，继续进入循环
```

- **温度参数（Temperature, $T$）的作用**：
  $$P(y_i) = \frac{\exp(z_i / T)}{\sum_j \exp(z_j / T)}$$
  - 当 $T \to 0$ 时，分布极度尖锐，等价于**贪婪搜索（Greedy Search，每次只挑概率最大的词）**，回答确定、死板。
  - 当 $T > 1$ 时，各词之间的差距被抹平，分布更平缓，模型更具创造性、发散性，但过高会产生胡言乱语（Hallucination）。
- **Top-P（核采样 Nucleus Sampling）的作用**：
  避免固定 Top-K 带来的生硬截断。当模型对预测非常自信时（首词概率 95%），Top-P 只挑 1 个词；当模型犹豫不决时，Top-P 动态展开候选池，保证句子的通顺与多样性平衡。

### 2.5 推理性能物理瓶颈：为什么 GPU 算力跑不满？(Roofline 内存墙)

在实际工程部署中，很多人会困惑：“为什么 80G 的 A100 显卡，在 Decode 生成文本时，GPU 计算核心利用率只有 5%~10%？”

这就涉及到计算机体系结构中的 **Roofline 性能模型**：

$$\text{算术强度 (Arithmetic Intensity)} = \frac{\text{浮点运算量 (FLOPs)}}{\text{内存访存量 (Memory Access Bytes)}}$$

1. **Prefill 阶段（GEMM 矩阵乘矩阵）**：
   输入序列长（$S$ 个词），权重矩阵一次搬入缓存可以被 $S$ 个输入重复复用，算术强度高（通常 $>100\text{ FLOPs/Byte}$）。此时性能受限于 GPU 算力峰值（TFLOPS），为 **计算受限（Compute-Bound）**。
2. **Decode 阶段（GEMV 矩阵乘向量）**：
   每一次推理只输入 1 个 Token。为了完成这 1 个 Token 的计算，GPU 必须把整整 7B / 70B 的全部模型权重从 HBM（显存）完整读取搬运进 SRAM 缓存一次！
   - 一个 7B 模型（14GB 权重），算 1 个 Token 的运算量仅约 $2 \times 7 \times 10^9 \approx 14\text{ GFLOPs}$。
   - 算术强度只有 $14\text{ GFLOPs} / 14\text{ GB} \approx 1\text{ FLOP/Byte}$！
   - **结论**：**Decode 阶段完全卡死在显存读取带宽（Memory Bandwidth）上**。GPU 计算核心在 90% 的时间里都在“等数据从显存搬过来”，这被称为 **“内存墙（Memory Wall）”**。因此，决定单个用户流式吐字速度的，不是 GPU 的算力有多高，而是显存带宽（如 HBM3 的 2~3 TB/s）有多大！

## 3. 专业实战测评题库 (含采分点与解析)

### 题 1 【系统工程显存计算题】
**题目**：某服务部署了 LLaMA-3 8B 模型进行线上客服对话。已知该模型配置为：$n_{\text{layers}}=32$，隐藏维度 $d=4096$，查询头数 $n_{\text{heads}}=32$，由于采用 GQA 技术，键值头数压缩为 $n_{\text{kv\_heads}}=8$，每个头的维度 $d_{\text{head}}=128$。系统采用 BF16 精度（每个参数 2 字节）存储 KV Cache。
1. 假设系统并发用户数（Batch Size）为 $b=16$，当对话上下文平均长度达到 $L=4096$ 时，仅 KV Cache 就需要消耗多少显存（以 GB 为单位，结果保留两位小数）？
2. 如果该模型没有使用 GQA，而是使用传统的多头注意力 MHA（即 $n_{\text{kv\_heads}}=32$），KV Cache 显存会达到多少？这对部署有何致命影响？

**采分点与解析**：
1. **GQA 显存推导（5分）**：
   - 套用公式：$\text{Mem}_{\text{KV}} = 2 \times n_{\text{layers}} \times n_{\text{kv\_heads}} \times d_{\text{head}} \times L \times b \times P$
   - 代入数值：
     $$\text{Mem}_{\text{KV}} = 2 \times 32 \times 8 \times 128 \times 4096 \times 16 \times 2 \text{ Bytes}$$
     $$= 65536 \times 4096 \times 32 \text{ Bytes} = 8,589,934,592 \text{ Bytes} = \frac{8,589,934,592}{1024^3} = \mathbf{8.00\text{ GB}}$$
2. **传统 MHA 对比与工程影响（5分）**：
   - 传统 MHA 的 $n_{\text{kv\_heads}}=32$，头数扩大 4 倍，显存消耗直接乘以 4：
     $$\text{Mem}_{\text{MHA}} = 8.00 \times 4 = \mathbf{32.00\text{ GB}}$$
   - **致命影响**：8B 权重本身占用约 16GB 显存。若在单张 24G 显卡（如 RTX 4090）上部署，MHA 下仅 KV Cache（32GB）就会直接导致显存彻底爆炸（OOM）；即便在 80G A100 上，MHA 也会将并发吞吐量压低 4 倍。GQA 将 KV Cache 压缩到 8GB，使多并发长文本服务成为可能。

### 题 2 【计算机系统结构辨析题】
**题目**：在很多大模型评测中，大家发现批量生成文本（如 Batch Size = 32）相比单个请求（Batch Size = 1），GPU 的整体吞吐量（Tokens per second）提升了十几倍，但单个请求的端到端延迟（Latency）几乎没有显著下降。请结合 Prefill 与 Decode 阶段的 Roofline 内存墙瓶颈，解释这一物理现象。

**采分点与解析**：
1. **Decode 阶段的访存绑定本质（5分）**：
   在单并发（$b=1$）时，生成 1 个 Token 需要把全部模型权重搬入片上缓存一次，GPU 算力利用率极低（算术强度 $\approx 1$），显存带宽被完全占满而计算单元大量闲置。
2. **批处理提升吞吐的机理（5分）**：
   当并发提升至 $b=32$ 时，权重矩阵从显存搬入一次，可以同时服务于 32 个不同的用户 Token 计算。访存量基本不变，但计算量扩大了 32 倍，算术强度提升了 32 倍，把原本闲置的 GPU Tensor Core 算力充分利用起来，因此总吞吐量大幅暴涨。但因为搬运权重的物理时间开销没有消除，单步前向传播的绝对耗时基本持平，所以单个用户的吐字延迟不会显著减少。

## 4. 极简复习闪卡 (CheatSheet)

| 概念与机制 | 核心物理本质（速查黄金定义） |
| :--- | :--- |
| **自回归推理本质** | **串行状态机**。输入历史全部词，预测下一个词，将新词追加到输入，循环执行 $N$ 次。 |
| **Prefill 阶段** | **计算受限 (Compute-bound)**。用户 Prompt 并行一网打尽，算力跑满，负责首字延迟 (TTFT) 并构建 KV Cache。 |
| **Decode 阶段** | **访存受限 (Memory-bound)**。每次只进 1 个词，算力闲置被显存带宽卡死（内存墙），负责流式吐字。 |
| **KV Cache 核心作用** | **空间换时间**。缓存历史 Token 的 $K, V$ 投影向量，避免每步重复计算，复杂度由 $O(N^2) \to O(N)$。 |
| **GQA 的真正价值** | **压缩 KV Cache 显存**。将 KV 头数压缩至 Query 头数的 $1/4 \sim 1/8$，使显存能容纳超长上下文与高并发。 |
| **Temperature 的实质** | **改变 Logits 分布平坦度**。$T \to 0$ 为贪婪确定性输出；$T > 1$ 增大候选词被选中的随机性。 |
