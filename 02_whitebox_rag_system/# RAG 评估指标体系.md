# RAG 评估指标体系

## 一、检索阶段指标

### 1. Context Recall：上下文召回率

Context Recall 关心的是：回答问题所需要的信息，有多少被检索出来了。

可以简单理解为：
该找的资料，有没有找全？

公式可以写成：
Context Recall = 被成功检索到的关键信息数量 / 回答该问题所需的全部关键信息数量

例如用户问：
“A 产品的退款政策和保修政策是什么？”

标准答案需要两个信息：
30 天内可退款；保修期为 1 年。

如果系统只检索到了退款政策，没有检索到保修政策，那么召回就不完整。

这个指标非常重要，因为 召回不足通常会导致答案缺失、答非所问，甚至模型自行补全不存在的信息。RAGAS 官方文档也把 Context Recall 列为 RAG 组件级评估指标之一。

### 2. Context Precision：上下文精确率

Context Precision 关心的是：检索出来的内容里，有多少是真的有用。

可以简单理解为：
找出来的资料是不是“干货”，还是混进了一堆无关内容？

公式可以写成：
Context Precision = 检索结果中相关内容数量 / 检索结果总数量

例如系统检索了 5 个 chunk，其中只有 2 个和用户问题真正相关，那么精确率就比较低。

Context Precision 低会带来两个问题：

* 第一，LLM 会被无关内容干扰。
* 第二，token 成本会升高，因为你把很多无用上下文也塞进了提示词里。

RAGAS 文档中也明确把 Context Precision、Context Recall、Faithfulness、Answer Relevancy 等作为 RAG 组件级评估指标。

### 3. Recall@K / Precision@K / Hit Rate

这几个是传统信息检索里常用的指标，在 RAG 中也很常见。

* **Recall@K 表示：** 前 K 个检索结果中，覆盖了多少相关文档？
* **Precision@K 表示：** 前 K 个检索结果中，有多少是相关的？
* **Hit Rate@K 表示：** 前 K 个结果里，只要命中至少一个相关文档，就算成功。

例如用户问一个问题，系统返回 top-5 文档。如果这 5 个文档里有一个文档包含正确答案，那么 Hit Rate@5 就算命中。

这类指标适合评估向量检索、BM25、混合检索、rerank 排序等模块。

### 4. MRR：Mean Reciprocal Rank

MRR 关注的是：
第一个正确结果排在第几位？

公式可以简单理解为：
MRR = 1 / 第一个相关结果的排名

* 如果第一个相关文档排第 1，得分是 1。
* 如果第一个相关文档排第 2，得分是 1/2。
* 如果排第 5，得分是 1/5。

MRR 很适合评估搜索排序质量。因为在 RAG 中，相关内容越靠前，越容易被模型重点利用。

### 5. nDCG：排序质量指标

nDCG 关注的是：
不同相关程度的文档，是否被合理地排在前面？

它比 Precision@K 更细，因为它不是简单判断“相关 / 不相关”，而是允许给文档打不同等级：

* 高度相关：3 分
* 部分相关：2 分
* 弱相关：1 分
* 无关：0 分

如果高度相关的文档排在最前面，nDCG 就高；如果关键文档被排到很后面，nDCG 就低。

## 二、上下文质量指标：不是找到了就够，还要看“内容能不能用”

检索结果不只是“相关”就够了，还要看它是否适合被大模型使用。

### 1. Context Relevance：上下文相关性

Context Relevance 评估的是检索出来的上下文和用户问题之间的相关程度。

TruLens 官方把 Context Relevance、Groundedness、Coherence 等列为可用于评估 AI 应用表现的指标。(trulens.org)

举个例子：
用户问：
“如何配置 Nginx 的反向代理？”

检索结果却返回：
“Nginx 的历史、作者、许可证信息。”

这段内容和 Nginx 有关，但和“反向代理配置”关系不大。它属于主题相关，但任务不相关。

这就是 Context Relevance 要解决的问题。

### 2. Context Utilization：上下文利用率

Context Utilization 关心的是：模型生成答案时，是否真的利用了检索到的上下文。

有时检索结果是对的，但模型没有使用它，而是依赖自己的参数知识回答。这在企业知识库、法律、医疗、金融等场景里非常危险。

例如知识库里明确写着：
“退款期限为 7 天。”

模型却回答：
“一般来说，退款期限为 30 天。”

这说明模型没有正确利用上下文。

RAGAS 文档中也包含 Context Utilization 这一类面向上下文使用情况的指标。(Ragas)

### 3. Noise Sensitivity：抗噪声能力

Noise Sensitivity 评估的是：当上下文中混入无关信息时，模型是否还能稳定回答。

真实业务里的检索结果很少是完美的。很多时候，top-k 里既有相关片段，也有无关片段。如果系统一遇到噪声就被带偏，说明它的鲁棒性不好。

例如用户问：
“A 合同的付款周期是多少？”

检索结果里有一段正确内容：
“付款周期为每 30 天一次。”

同时混入另一段无关内容：
“B 合同的付款周期为每 60 天一次。”

如果模型回答成 60 天，就说明系统抗噪声能力差。

RAGAS 官方指标列表中也包含 Noise Sensitivity。(Ragas)

## 三、生成质量指标：回答是否可信、相关、完整？

检索阶段解决的是“资料找得怎么样”，生成阶段解决的是“答案写得怎么样”。

### 1. Faithfulness / Groundedness：忠实性 / 有依据性

这是 RAG 评估里最重要的指标之一。

Faithfulness 关心的是：模型生成的答案，是否能被检索到的上下文支持。

DeepEval 官方文档对 Faithfulness 的定义是：用 LLM-as-a-judge 判断 RAG 生成器的输出是否与 retrieval context 在事实层面对齐；它更关注输出和检索上下文之间是否存在矛盾。(DeepEval)

简单说：
答案中的每一句事实，都能不能在检索材料中找到依据？

例如上下文是：
“A 产品支持 7 天无理由退款。”

模型回答：
“A 产品支持 30 天无理由退款。”

这就是不忠实。即使“30 天退款”在现实中很常见，只要它不被当前上下文支持，在 RAG 评估里就应当扣分。

Faithfulness 可以近似写成：
Faithfulness = 答案中可被上下文支持的事实陈述数 / 答案中的全部事实陈述数

注意，Faithfulness 不是判断“世界知识是否正确”，而是判断“答案是否忠实于检索材料”。

### 2. Answer Relevancy：答案相关性

Answer Relevancy 评估的是：答案有没有真正回答用户的问题。

比如用户问：
“RAG 中 rerank 的作用是什么？”

模型回答：
“RAG 是检索增强生成，常用于知识库问答。”

这句话本身可能没错，但没有回答 rerank 的作用，所以 Answer Relevancy 不高。

RAGAS 官方文档也把 Answer Relevancy 作为重要指标之一。(Ragas)

### 3. Answer Correctness：答案正确性

Answer Correctness 关注的是：最终答案和标准答案是否一致。

它通常需要 reference answer，也就是人工标注的标准答案。

例如：
用户问题：
“公司年假的最少提前申请时间是多少？”

标准答案：
“至少提前 3 个工作日申请。”

模型回答：
“需要提前 3 天申请。”

这个答案大体正确，但“3 天”和“3 个工作日”存在细微差异，具体业务里可能要扣分。

Answer Correctness 适合用在有标准问答集的场景，比如客服知识库、企业制度问答、考试题库等。

### 4. Completeness：完整性

Completeness 评估的是：答案有没有覆盖问题所需的所有要点。

例如用户问：
“RAG 的评估指标有哪些？”

如果回答只讲了 Faithfulness 和 Answer Relevancy，却没有讲检索召回、上下文精确率、端到端评估，那就是不完整。

完整性尤其适合评估多要点问题，比如：

* “请分别说明 A、B、C 三种方案的优缺点。”
* “请总结这份合同中的付款、违约、终止条款。”

### 5. Citation Accuracy：引用准确性

很多 RAG 系统会要求模型给出引用来源，比如文档编号、段落 ID、网页链接等。

Citation Accuracy 关注的是：答案引用的来源是否真的支持对应结论。

常见错误包括：

* 引用了不存在的文档；
* 引用了相关但不能支持该结论的文档；
* 答案是对的，但引用位置错了；
* 多个引用混在一起，无法对应具体事实。

如果你的 RAG 系统面向严肃场景，比如论文问答、法律检索、企业合规、医疗知识库，引用准确性非常重要。

## 四、端到端指标：用户最终是否满意？

前面的指标都是局部指标。真正上线时，还要看整体效果。

### 1. End-to-End Accuracy：整体准确率

最直接的指标是：
整体准确率 = 回答正确的问题数量 / 总问题数量

它适合有标准答案的数据集。

但它的问题也很明显：
它只能告诉你“系统错了”，不能告诉你“错在哪里”。

所以端到端准确率必须和检索指标、生成指标一起看。

### 2. Human Preference：人工偏好

有些问题没有唯一标准答案，比如：

* “帮我总结这份报告。”
* “给我推荐一套学习路线。”
* “解释一下这个技术方案的风险。”

这时可以让人工评估者比较两个系统的答案：

* A 更好
* B 更好
* 差不多
* 都不好

这种方式适合评估可读性、逻辑性、表达质量和用户体验。

### 3. Task Success Rate：任务成功率

在业务场景里，最终要看用户任务是否完成。

例如客服 RAG：

* 用户是否解决问题？
* 是否减少转人工？
* 是否减少重复提问？

例如企业知识库 RAG：

* 员工是否找到制度答案？
* 是否减少查文档时间？
* 是否能准确定位原文？

任务成功率比单纯的文本相似度更贴近真实业务价值。

## 五、RAG 指标之间的关系：怎么定位问题？

做 RAG 评估时，最重要的不是看单个分数，而是通过指标组合定位问题。

### 情况一：Context Recall 低，Faithfulness 高

这说明模型很忠实，但检索没找全资料。

**表现通常是：**
答案没有胡编，但回答不完整。

**优化方向：**

* 改进 chunk 切分
* 优化 embedding
* 增加 top-k
* 加入 hybrid search
* 增加 query rewrite

### 情况二：Context Precision 低，Faithfulness 低

这说明检索结果里混入了太多噪声，模型又被噪声带偏。

**表现通常是：**
答案看起来很丰富，但夹杂错误信息。

**优化方向：**

* 加入 rerank
* 减少 top-k
* 改进 chunk 粒度
* 增加 metadata filter
* 优化召回后的排序

### 情况三：Context Recall 高，但 Answer Relevancy 低

这说明资料找到了，但模型没有围绕用户问题组织答案。

**表现通常是：**
上下文是对的，但回答跑题。

**优化方向：**

* 改 prompt
* 明确回答格式
* 要求先判断问题意图
* 要求只回答用户所问

### 情况四：Context Recall 高，Answer Relevancy 高，但 Faithfulness 低

这说明检索和问题匹配都没问题，但生成阶段出现幻觉。

**表现通常是：**
答案方向对，但细节编造。

**优化方向：**

* 降低 temperature
* 要求逐条引用依据
* 要求没有依据就回答“不知道”
* 增加事实核查步骤
* 使用更强的生成模型

## 六、一个实用的 RAG 评估指标体系

如果你是刚开始做 RAG，我建议不要一上来就堆十几个指标。可以先用下面这套最小指标集。

### 第一层：检索指标

* Context Recall
* Context Precision
* Hit Rate@K
* MRR

**它们回答：**

* 资料有没有找对？
* 资料有没有找全？
* 正确资料排得靠不靠前？

### 第二层：生成指标

* Faithfulness
* Answer Relevancy
* Answer Correctness
* Completeness

**它们回答：**

* 答案有没有依据？
* 有没有回答用户问题？
* 和标准答案是否一致？
* 要点是否完整？

### 第三层：业务指标

* 用户满意度
* 任务成功率
* 转人工率
* 平均解决时长差评率

**它们回答：**
这个 RAG 系统到底有没有业务价值？

## 七、不要只看一个“综合分”

很多 RAG 评估框架会给出一个总分，但我不建议只看总分。

原因很简单：
同样是 80 分，一个系统可能是检索差，另一个系统可能是生成差。

这两个问题的优化方向完全不同。

正确做法是把 RAG 拆开看：

* 检索是否召回？
* 上下文是否相关？
* 答案是否忠实？
* 答案是否回答问题？
* 用户是否满意？

RAGAS 的设计思想也是对 RAG pipeline 的不同组件进行单独评估，而不是只给一个模糊总分。(Ragas)

---

## 八、总结

RAG 的评估可以用一句话概括：
先评估“有没有找对资料”，再评估“有没有基于资料正确回答”。

### 核心指标可以分成四类：

* **检索质量：**
Context Recall、Context Precision、Hit Rate@K、MRR、nDCG
* **上下文质量：**
Context Relevance、Context Utilization、Noise Sensitivity
* **生成质量：**
Faithfulness、Answer Relevancy、Answer Correctness、Completeness、Citation Accuracy
* **业务效果：**
Task Success Rate、Human Preference、用户满意度、转人工率

### 如果只记住几个最重要的，我建议是：

* **Context Recall：** 该找的有没有找全
* **Context Precision：** 找出来的有没有用
* **Faithfulness：** 答案有没有依据
* **Answer Relevancy：** 有没有回答用户问题
* **Answer Correctness：** 最终答案对不对

最后，评估 RAG 的关键不是为了得到一个漂亮分数，而是为了定位问题：

* 是检索没找对？
* 是上下文太脏？
* 是模型没看懂？
* 还是模型看懂了但乱编？

只有能定位问题的评估，才是真正有用的评估。
